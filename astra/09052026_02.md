# GigHound implementation plan — September 5, 2026

This plan was written at the audit-only checkpoint. Implementation was subsequently authorized; current changes and remaining work are tracked in [09052026_04.md](09052026_04.md). The audit register is [09052026_01.md](09052026_01.md); execution evidence and reproductions are in [09052026_03.md](09052026_03.md).

The project has useful foundations, but its highest-value promise—finding suitable work and sending precisely reviewed proposals—currently breaks at several integration boundaries. Stabilize that loop before expanding platform coverage or increasing automation volume. The 62 findings include four critical issues, 32 high-priority issues, 23 medium-priority issues and three low-priority improvements; severity includes conditional risks and is not a count of observed production incidents.

## Implementation rules

1. Preserve human approval for the exact content, account, destination, request type and spending parameters. Any material change invalidates approval.
2. An uncertain external action is a reconciliation case. It must never automatically become a retryable failure or a confirmed success.
3. Keep domain transitions, audit events and work intent in one database transaction. Publish work through a durable outbox; external actions cannot be made transactional with Postgres, so reconcile them explicitly.
4. Use one implementation behind every API entry point. Remove legacy dispatch logic after compatibility tests and a deprecation path.
5. Every finding becomes a small issue with its audit ID, concrete failing example, owner, acceptance test and rollback approach. Convert defect-asserting audit proofs into correctness regression tests during implementation.
6. Do not rewrite the application wholesale. Preserve proven tenant helpers, the vault, existing migrations, tests and frontend components while correcting their contracts.
7. Fixes require evidence under the actual deployment stack. Passing SQLite tests alone is insufficient for locking, migration, JSON and connection-pool behavior.

## P0 — Establish a safe baseline and supported product contract

**Owner:** technical lead + product/integration owner. **Dependency:** none.

1. Preserve the audited commit and create an implementation branch. Inventory existing live proposals/tasks by state using read-only reports, without modifying ambiguous external outcomes.
2. Take a restorable database backup and preserve the matching vault key securely. Test restoration in a disposable environment before any data migration.
3. Define the supported platform capability matrix: discovery, drafting, messages, proposal submission, outcome sync, gig editing and required permissions/scopes. Validate current official APIs/MCP and deployment-specific approvals; do not rely on historical marketing claims.
4. Define exact approval, confirmation, cancellation, retry and monetary-unit contracts. Choose the initial commercial wedge: dependable discovery + evidence-based drafting + safe review, with only demonstrated submission channels.
5. During implementation rollout, contain A001/A002/A004/A013 first: restrict global circuit controls, disable duplicate legacy dispatch, and prevent blind submission-task replay. Keep a reviewed manual workflow available while external-write safety is incomplete.
6. Create an end-to-end synthetic tenant fixture and fake provider that records every attempted external action. Capture baseline activation, first-draft latency, review effort and confirmed submission rates.

**Deliverables:** capability matrix, transition specification, rollback/restore evidence, prioritized issue board and end-to-end fixture.

**Exit:** every externally writable channel has a known permission basis and testable action contract; risky paths have controlled rollout gates. No live submissions are used as speculative tests. See A056 and the critical findings.

## P1 — Repair approval, dispatch and browser execution

**Owner:** backend/worker engineer. **Dependency:** P0; the tenancy containment for A013 belongs in the first implementation patch even though the full security work is P2.

1. Build a single submission domain service. Require owned account + provider + request type + expected proposal version + immutable approved text/bid snapshot.
2. Route main and legacy APIs through it. Use conditional transitions to reject repeated clicks, competing approvals, stale edits and cross-platform dispatches.
3. Create submission-intent/task/audit records atomically. Replace helper commits with flushes where transaction ownership belongs to the caller. Use an outbox for broker publication.
4. Give each worker claim a unique expiring lease/fencing token. Replays of read tasks can be safe; submission tasks require a dispatch checkpoint and reconciliation after worker death, timeouts or uncertain responses.
5. Replace generic boolean completion with explicit confirmed_submitted, confirmed_not_submitted, uncertain and manual_action_required results. Require provider receipt/verified marker where available.
6. Separate message follow-ups from new applications/bids. Require confirmed parent submission and a supported conversation destination; otherwise supply a clear manual copy workflow.
7. Correct approved/humanized text precedence and typing-plan invalidation. Support Unicode and compare final form values against the approved snapshot before any irreversible action.
8. Version the Fiverr task schema. Render structured descriptions, preserve package pricing/delivery/revisions and explicitly handle unsupported fields. Do not claim that saving a partial form completed a full gig draft.
9. Replace the headless filled-form handoff with either a secure interactive takeover or explicit manual instructions/export. Build safe resolution controls for failed and unverified outcomes.

**Acceptance:** the fake provider sees exactly the approved text once across duplicate API calls, concurrent review/submit, lost responses and worker death before/after dispatch. Tests cover Unicode, the UI’s real Fiverr template payload, unknown verdicts, delayed completions, follow-up messaging and recovery without duplicate external actions.

**Rollout/rollback:** add new state/event fields before switching writers. Drain or explicitly classify old tasks. Disable new dispatch to roll back; never downgrade uncertain submissions to pending. Preserve records needed for reconciliation.

## P2 — Enforce tenant, account and credential boundaries

**Owner:** security/backend engineer. **Dependency:** P0; complete before broad multi-tenant use.

1. Split tenant circuit controls from privileged global operations. Derive reviewer/audit actor identity from authentication; retain any display label as descriptive metadata.
2. Make account ID the stable link between credentials, configuration, tasks, platform receipts and browser profiles. Prevent ambiguous duplicate identities and transactionalize identity changes/deletion.
3. Enforce account disable, credential revocation and tenant deletion at claim and immediately before external writes. Propagate credential epochs to workers, invalidate cached contexts and require erasure acknowledgments.
4. Replace the shared worker trust model with per-worker identity and task-scoped session/result capabilities. Require fencing tokens, expected task items/platforms and immutable result digests.
5. Repair provider credential schemas, refresh metadata and principal selection. Add read-only connection tests. Remove unsupported password enrollment until a real, supported enrollment flow exists.
6. Implement single-use OAuth transactions bound to user/account/redirect URI; validate state and use PKCE where supported. Prevent non-default enrollment from overwriting unrelated default credentials.
7. Validate browser navigation and storage-state origins, enforce destination/redirect rules and isolate egress. Do not treat an HTTP scheme check as sufficient SSRF protection.
8. Introduce durable session versions, enforce logout/password revocation and same-second behavior, and expire/revoke active WebSockets. Release database sessions before long-lived socket loops.
9. Bind digest delivery to a verified tenant destination; add timeouts and send idempotency. Correct agency-log ownership, retention and lifecycle handling.
10. Apply consistent strict schemas, UTF-8 password limits, workload/body/list limits, finite monetary values and owned foreign references. Correct local secret-file permissions as an explicit implementation change and verify deployment secret handling.

**Acceptance:** a two-tenant matrix covers reads, writes, references, OAuth, email, worker session/results and deletion. Disabled/deleted accounts cannot execute queued actions. Redis failure cannot silently defeat security changes. Many idle WebSockets do not consume HTTP DB capacity. Malformed/oversized input returns bounded validation errors.

**Rollback:** add and backfill account/session identity fields before enforcement. Deploy readers capable of both versions temporarily, but never reopen cross-tenant permissions as a compatibility fallback.

## P3 — Make discovery and generation reliable and bounded

**Owner:** pipeline/backend engineer. **Dependency:** state/identity contracts from P1–P2.

1. Define explicit profile semantics: no configuration, all auto-queue disabled, unrestricted platforms and unsupported selections are different states.
2. Replace competing per-profile locks with fair per-account/platform scheduling or coalesced searches. Store run history and explain skipped, failed, empty and successful results separately.
3. Make keyword/filter scoring profile-local where appropriate, with a separate explicit global exclusion layer. Record which profile and reasons qualified each job.
4. Upsert source changes with observed timestamps. Rescore when budgets/competition change and check expiry before review/submission.
5. Persist discovery/generation work intent and reconcile missing drafts after broker outages. Claim generation by proposal/job version before calling the LLM; a stale worker cannot overwrite later human decisions.
6. Separate worker read/write priorities so off-hours read backlog does not hide approved submissions. Use bounded pages, fairness and task-age reporting.
7. Implement shared account/action rate budgets, atomic quota reservations and a distinction between draft creation and actual sending. Resolve half-open circuit trials from the owning task’s outcome; keep manual stops explicit.

**Acceptance:** three profiles on one platform all receive service; all-disabled profiles produce zero automatic drafts; unsupported-only selection performs no unrelated searches; broker outage/restart eventually produces one draft; duplicate generation cannot reset approved content; a submission behind 50 off-hours reads remains visible to the worker; quotas hold under concurrent processes.

**Rollout/rollback:** shadow-log eligibility/fairness decisions before switching scheduling. Use rate budgets and per-tenant feature flags to cap initial throughput. Preserve the outbox on rollback.

## P4 — Repair ranking, learning and monetary correctness

**Owner:** data/backend engineer with product review. **Dependency:** trustworthy action events and normalized account identity.

1. Create an idempotent outcome/event model. Repeated outcomes are no-ops; corrections reverse or recompute derived statistics. Disallow hired outcomes on unsent drafts without an explicit imported historical-event workflow.
2. Introduce explicit money currency and billing units, decimal values and dated FX provenance. Keep unknown currency distinct from USD. Separate hourly/fixed/annual amounts in normalization, display and learning.
3. Ground freelancer capabilities in verified profile/portfolio evidence. Never use the job’s requirements as possessed skills. Omit invented experience/support commitments and expose evidence gaps to reviewers.
4. Store template/model/prompt/profile/version provenance. Separate suggestion impressions from selected templates, confirmed submissions and outcomes. Use sample counts/uncertainty in ranking.
5. Use stable provider IDs for client history. Label heuristic cohorts as similarities, not known clients.
6. Record actual submitted/replied/outcome timestamps. Define current inventory separately from cohort funnels; schedule follow-ups from confirmed submission time.
7. Use exact proposal references and structured/uncertain status mapping. Reject unlisted task result items and signal selector coverage loss. Make gig metrics idempotent and preserve missing measurements as unknown.
8. Rebuild affected aggregates from trustworthy events. Where history is ambiguous, mark it unknown and retain the original records rather than manufacturing precision.

**Acceptance:** repeat/corrected outcomes yield the same aggregates as recomputation; empty user capability evidence yields no asserted skills; EUR/hour and USD/fixed samples cannot mix; delayed submission yields the correct trend week and follow-up date; identifier 123 never matches 1234; missing metrics never become fabricated zeros.

**Rollback:** preserve raw original values and add versioned normalized columns/events. Compare old/new analytics in shadow mode; do not overwrite historical evidence irreversibly.

## P5 — Complete the user journeys

**Owner:** frontend/product engineer. **Dependency:** stable P1–P4 APIs.

1. Fix first-event consumption and test bursts, reconnects and session changes. Add request ordering/cancellation and coherent cache invalidation for lists.
2. Bind drafts to server versions. Warn on stale edits, preserve work safely and require explicit resolution of conflicts. Correct password/session messaging and display actionable API errors.
3. Build platform-specific setup for seller username, agency roster, account selection, credentials and reenrollment. Replace presence-based readiness with verified capabilities and last-successful-run status.
4. Make recovery a first-class queue: uncertain submissions, failed generation, missing credentials and expired sessions each have a clear next action.
5. Finish focus trapping/restoration and label associations in the existing Modal/form system. Keep its working dialog semantics/Escape handling. Test keyboard navigation and meaningful validation announcements.
6. Add URL-backed navigation and filters. Label unsupported/preview features accurately; remove dead controls from the primary workflow until their backend/worker path exists.
7. Persist onboarding progress and per-user dismissal; compute attention counts server-side, with last updated indicators and refresh after actions.

**Acceptance:** a new user can connect a supported account, run a meaningful search, review the exact draft, safely submit/record a manual send, resolve an uncertain outcome and understand the results without API calls outside the UI. Keyboard-only completion works; a first incoming client reply is visible; two tabs cannot silently overwrite each other.

**Rollback:** ship behind UI flags while retaining compatibility with deployed APIs. Preserve user drafts and expose recovery actions independently of cosmetic redesign.

## P6 — Production assurance, migrations and maintainability

**Owner:** platform/test engineer. **Dependency:** starts with test infrastructure in P0, release gate after P1–P5.

1. Add isolated Postgres/Redis test services and validate endpoint behavior against them. Replace fixed localhost FLUSHDB tests with explicitly owned disposable resources.
2. Add historical dirty-data migration fixtures, especially duplicate live proposals, and read-only deployment preflights. Never delete a possible submitted duplicate merely to satisfy a unique index.
3. Add actual Chromium typing/handler contract tests and synthetic full-journey frontend tests. Keep external providers mocked for routine CI; validate live selectors only in approved, controlled integration environments.
4. Add readiness, worker heartbeats, outbox/queue age, error/uncertain-action metrics and operator alerts. Separate process liveness from capability health.
5. Test broker persistence/reconciliation, database+vault-key restores, worker artifact erasure, tenant deletion and retention. Define backup ownership, recovery objectives and periodic restore drills.
6. Profile realistic data sizes. Page provider threads/history, bound all-tenant/all-template scans, scope preview invalidations, and add composite indexes after EXPLAIN/benchmark evidence. Set tested resource limits.
7. Refactor duplicated dispatch/transaction code and large UI components around tested contracts. Migrate deprecated config APIs, align dev installs with runtime locks, audit exact deployed artifacts, pin base-image digests and trim frontend Docker context.
8. Run a staged canary with representative consenting users. Track confirmed actions, unknown outcomes, wrong-account/content incidents, queue delay and support burden. Expand only when correctness and recovery gates hold.

**Exit:** no unresolved critical findings; high findings either fixed or explicitly contained with documented ownership and dates. CI proves the deployed stack’s important behaviors, migrations handle historical data, restore/erasure drills pass and users can recover from expected failures.

## P7 — Ten feature proposals with measurable value

These are product bets, not promises of exponential growth. Each extends the existing app with a distinct user-facing capability and needs a baseline/control comparison. Shared prerequisites are trusted identity, evidence, event timestamps and outcome accounting from P1–P6.

| ID | New capability | User and sales value | First useful release | Success measure |
|---|---|---|---|---|
| F1 | **Daily opportunity brief optimized for net value and available capacity** | Turns a feed into a short, realistic work plan; sells saved time and better-fit work rather than proposal volume. | Rank a small shortlist by fit, freshness, estimated effort/cost and available hours; show reasons and uncertainty. | Qualified conversations and net booked value per hour spent reviewing. |
| F2 | **Evidence-backed proposal studio** | Every experience/result claim links to a verified portfolio item; reviewers can inspect support before approving. | Claim-to-evidence highlighting, unsupported-claim warnings and a reusable proof library. | Review time, factual correction rate and qualified reply rate. |
| F3 | **Personal fit coach** | Learns a freelancer’s preferred scope, industries, red flags and deal-breakers; makes ranking explainable. | Explicit accept/reject feedback, profile-specific explanations and a comparison against the fixed scorer. | Precision among the top-ranked jobs and retention of recommendations users choose. |
| F4 | **Unified conversation and next-action inbox** | Converts reply alerts into a workflow that helps users win the conversation, with context and reminders. | Authorized thread sync or user import, reply drafts, unanswered-task ownership and human-approved sending. | Time to first reply and interview-to-contract conversion. |
| F5 | **Scope and pricing workbench** | Makes proposals economically defensible with milestones, effort ranges and clear assumptions. | Currency/unit-safe cost and margin scenarios, capacity checks and editable statement-of-work drafts. | Estimate error, accepted proposal value and realized margin where users supply outcomes. |
| F6 | **Agency workspace with roles and review assignment** | Creates a higher-value team tier without sharing passwords or losing accountability. | Owner/reviewer/contributor roles, explicit account assignments, workload distribution and audit history. | Team activation, approval turnaround and seats retained per workspace. |
| F7 | **Concierge setup and connection doctor** | Reduces the expertise needed to get value; makes account problems understandable and recoverable. | Guided profile/portfolio import, provider-specific setup, connection tests and a synthetic first successful workflow. | Time to first useful draft and setup completion without support. |
| F8 | **Client relationship workspace** | Helps freelancers build repeat business instead of repeatedly starting cold. | Stable-ID client records, notes, past outcomes, permitted contact imports and repeat-engagement reminders. | Repeat-client work share and conversations converted from existing relationships. |
| F9 | **Controlled proposal/gig experiment lab** | Gives users evidence about which wording, positioning and package changes improve results. | Human-approved variants, tracked exposure/selection, bounded experiments and confidence-aware reports. | Measured lift over the user’s baseline with minimum sample requirements. |
| F10 | **Revenue attribution and shareable ROI reports** | Makes subscription value visible and gives teams/client-facing freelancers a credible business review artifact. | Attribute confirmed pipeline outcomes to source/profile/effort/cost, import realized revenue and export redacted reports. | Attributable value, reporting usage, retention and willingness to pay. |

**Pragmatic delivery order:** pilot F7 and F2 first, then F1 and F4. Add F5/F8 once event and monetary data are trustworthy. Release F6 only after real workspace-level authorization is tested. F9 needs enough reliable outcomes to avoid false conclusions; F10 needs explicit attribution rules and user-provided revenue/cost data. User research and measured adoption should decide further investment.

**Commercial packaging hypothesis:** a solo tier centered on discovery/review/evidence, a professional tier adding conversations/pricing/relationship tools, and an agency tier adding roles/assignment/reporting. Validate demand and operating cost before setting prices or promising returns. Integrations are sold according to demonstrated permitted capability, not the number of platform logos.

## Definition of completion

Implementation is complete when each audit ID has a linked change or documented accepted limitation, tests cover its actual failure mechanism, historical data has a safe migration/reconciliation path, deployment and recovery checks pass, and the primary user journey works without hidden operator intervention. Feature experiments have separate success criteria and should not delay urgent correctness/security remediation.
