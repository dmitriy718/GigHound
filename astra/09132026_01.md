# GigHound remaining-work and release-readiness audit — September 13, 2026

Audit only. No application fixes, deployment, provider submissions, or live database changes were performed. This report and its isolated reproduction scripts/logs are the only intentional repository additions in this audit. Build/test tools also produced ordinary generated artifacts.

## Decision

The current source is not yet qualified for a broad public production launch. It contains useful, tested discovery, proposal review, tenant isolation, durable generation, and manual reconciliation workflows. However, newly reproduced submission/control defects, incomplete customer operations, and unqualified live integrations prevent a defensible claim of mass-market readiness.

This is an evidence-backed register from repository-wide inventories, focused control-flow review, isolated reproductions, the existing audit reconciliation, and fresh automated checks. It is not a mathematical guarantee that every latent defect has been found. No real provider account, live customer data, production infrastructure, throughput target, or commercial conversion funnel was qualified in this audit. Previous findings are not automatically repeated as still broken: September 5's fixes were reviewed as the current baseline.

Baseline: branch `astra/implementation-20260905`, HEAD `4f628609ac74ddd3b4bcaa0492435fa8d63b65e5`. The working tree already contained 128 changed/untracked entries when inspected; HEAD alone does not represent the reviewed application. Preserve and review that work before creating a release candidate.

## Ranked register: hardest first

Difficulty is a relative engineering estimate, not a delivery promise. Scores include migration, integration, and validation complexity. Equal scores are approximately tied. **Blocker** means fix before the affected capability is exposed publicly; **launch gate** means evidence/configuration is required; **expansion** may ship later if the product is accurately limited. The recommended execution sequence follows the register and prioritizes risk and dependencies instead of difficulty alone.

### R01 — Qualify the actual end-to-end provider channels — 10/10 — Launch gate / unfinished integration

**Evidence:** `docs/operations.md:7` capability matrix; `worker/platforms.py:147` explicitly says submission markers require live validation; `worker/handlers/gig_draft.py:35` returns `manual_action_required` for structured package templates; `worker/handlers/manual_assist.py:64` retains manual outcomes. `backend/app/workbench.py:430` reports live connection verification as false.

**Remaining work:** Establish a tested, account-specific capability matrix for discovery, authorization refresh, drafting, submission, receipts and outcomes. Structured Fiverr package editing, persistent interactive browser takeover and automated follow-up sending are not finished automated features. Manual paths are deliberate containment, not an accidental missing return statement.

**Done when:** Each offered channel has permission/capability evidence, representative contract fixtures and a controlled live canary with independently verified results. Unsupported operations are clearly gated. Building every possible channel is an expansion choice, not a requirement to sell a narrower useful product. No current provider-policy claim is inferred from the code or an agency subscription.

### R02 — Finish explicit multi-account selection through the whole workflow — 9/10 — Confirmed defect / functional limitation

**Evidence:** `backend/app/approval.py:16` selects at most two enabled accounts and considers more than one ambiguous; there is no per-proposal account choice in this snapshot function. `backend/app/adapters/accounts.py:8` rejects multiple accounts. Constructors outside error handling occur in `backend/app/routers/adapters.py:67`, `:105`, `:112`, and agency endpoints. P4 reproduces an uncaught `AdapterAuthError` in the quota endpoint with two valid active accounts. The legacy Freelancer bid route also constructs a default adapter after canonical submission.

**Impact:** Enrolling another valid account can make approval/dispatch unavailable and produce server errors in account utilities. A compatibility call can encounter account-selection failure after its canonical action has already completed.

**Done when:** Search, proposal review, immutable snapshots, task payloads, quotas, outcome polling and account utilities carry an explicit owned account identity; ambiguity returns actionable validation errors; multi-account browser and API journeys pass.

### R03 — Qualify scale, fairness and operating cost — 9/10 — Launch gate / unfinished engineering

**Evidence:** `backend/app/tasks.py:240` discovery fan-out still loads all profile pairs; `:415` generation-failure retry loads all matching items; `:652` reaper loads all expired claims. `backend/app/digest.py:48` loads all eligible alert settings. Existing bounded tenant fan-out and index tests do not bound these separate paths. `docs/operations.md:67` explicitly disclaims production load qualification. Large views/routes remain tightly coupled: ProposalQueue 1,164 lines, GigManager 940, proposal router 771 at inspection.

**Done when:** Define target active tenants, discovery volume, browser throughput, acceptable latency and infrastructure cost; batch remaining scans, bound queues and provider work, measure fair scheduling and failure recovery under sustained load, and size DB/worker pools. Decompose risky modules incrementally around these changes rather than blocking a pilot on a cosmetic rewrite.

### R04 — Build a customer payment and entitlement lifecycle if selling GigHound as SaaS — 9/10 — Missing commercial capability, conditional scope

**Evidence:** Inventory of mounted routers in `backend/app/main.py:63` and searches of backend/frontend found no customer checkout, subscription model, billing webhook handling or paid-plan entitlement enforcement. Existing `billing_unit` means a job's rate unit, and Workbench revenue records track users' receipts; neither charges GigHound customers.

**Done when:** A chosen commercial model supports payment, idempotent provider events, paid access, usage limits, cancellation and payment-failure handling, with reconciled customer records and test-mode journeys. Also provide the appropriate public purchase/onboarding/support information. This is required for self-service SaaS sales, not for using GigHound privately to win freelance work. Do not implement a speculative billing model without selecting that business scope.

### R05 — Finish browser-worker production isolation — 8/10 — Launch gate / security hardening

**Evidence:** `worker/security.py:8` validates HTTPS hostnames; it does not enforce resolved network destinations. `docs/operations.md:26` explicitly requires private/reserved-address and DNS-rebinding egress controls and exclusive session volumes. `docker-compose.worker.yml` supplies one shared named session volume for the worker service, with no per-replica assignment.

**Done when:** Deploy distinct worker identities and exclusive profiles, verified outbound network restrictions, encrypted/retired-volume handling, and credential-revocation drills. Test denied destinations and worker replacement. This audit demonstrates missing deployment controls, not a reproduced exploit against a provider domain.

### R06 — Make automatic circuit state durable and conservative during outages — 8/10 — Confirmed safety defect

**Evidence:** `backend/app/circuit_breaker.py:69` returns local state or `closed` after Redis misses; `:96` stores automatic transitions in Redis/local memory. P5 reproduces open → closed after process-state loss with unavailable Redis. `backend/app/send_budget.py:64` only consults durable trial ownership when cached state says `half_open`; `routers/gigs.py:481` authorizes based on the same state. `send_budget.py:116` also changes cached trial state before the surrounding SQL commit.

**Impact:** A fresh API process can forget an automatically tripped stop and bypass the intended trial gate while a browser task is still claim-valid. Persistent manual stops are separately stored in SQL and are not the defect reproduced here.

**Done when:** SQL owns automatic stops and trial transitions or unavailable state blocks action; commit and cache ordering cannot advertise a permission that failed to commit; multi-process broker-loss and recovery tests pass.

### R07 — Finish generation exhaustion, crash recovery and retry administration — 7/10 — Confirmed broken recovery

**Evidence:** `backend/app/work_queue.py:23` requires attempts <3 to claim; `:68` refuses all `running` rows, even expired ones. P2 creates an expired third-attempt running intent and proves both claim and reset fail. `backend/app/tasks.py:402` also excludes exhausted attempts. `routers/proposals.py:510` exposes reset through an existing proposal item, while an intent can exist before any proposal row is produced.

**Done when:** Expired exhausted work reaches an explicit terminal state; authorized manual retry can safely reset expired work without reviving active leases; users/operators can inspect and retry job intents without a proposal row; scheduling has bounded fair ordering and clear attempt/error history.

### R08 — Complete exact money storage and pricing semantics — 7/10 — Known limitation / improvement

**Evidence:** `backend/app/models.py:104`, `:176`, `:299`, `:394`, `:409` use Float for budgets, rates, bids, gig pricing and revenue. `docs/operations.md:50` documents approximate scoring FX. Workbench uses Decimal, but that does not migrate legacy financial columns.

**Done when:** Use a deliberate exact-money model and currency-specific rounding, migrate historical values without inventing precision, preserve native currency/rate units, and test bid/export/report boundaries. This is not proof that every current amount is wrong. Prioritize before offering accounting-grade reports or automated monetary optimization.

### R09 — Finish production backup, recovery and migration release controls — 7/10 — Launch gate / operational gaps

**Evidence:** `scripts/backup_restore.py:26` supports only 256 MiB dumps; it dumps first and then checks size, and restores the DB before writing the matching key file (`:161`). `scripts/deployment_preflight.py` detects dangerous historical states but does not reconcile them. `backend/Dockerfile` CMD migrates at API startup even though Compose also supplies a migration job.

**Done when:** Schedule protected off-host backups, alert on failures, test realistic restore size/time and matching-key recovery, preflight writable key output, define recovery objectives, reconcile historical queues, and serialize release migrations. Prove a rollback without replaying uncertain external submissions. The earlier small disposable restore drill does not supply a production recovery service.

### R10 — Finish self-service identity, account recovery and abuse controls — 7/10 — Missing features / confirmed fallback behavior

**Evidence:** `backend/app/routers/auth.py` has registration/login/password-change but no forgotten-password reset or verified-email flow; `:95` explicitly calls verification planned. Rate-limit failures return without throttling (`:44`, `:71`). `backend/app/auth.py:42` checks JWT secret presence but not minimum strength. Default registration is enabled in `backend/app/config.py:21`.

**Done when:** Deliver verified email and safe recovery, robust per-account/IP abuse admission during cache outages, appropriate secret validation and session recovery tests. Set public-registration policy explicitly. The test suite's weak synthetic-key warnings are not evidence that the deployment uses a weak key.

### R11 — Enforce the reviewed browser form before any Upwork submission — 7/10 — Confirmed blocker

**Evidence:** `worker/handlers/upwork_proposal.py:22` silently skips missing agency/member selectors; bid entry around `:89` also silently skips a missing input. The handler then clicks Submit. P7 reproduces a submit click with all three controls absent. Both agency and member selectors are given the same member label. `backend/app/routers/gigs.py:474` checks task account/text but does not compare every task financial/destination/member field to the approval snapshot; the worker prefers `humanized_text` when supplied.

**Done when:** Require and read back the reviewed identity, bid, text, destination and applicable terms, with explicit handling of platform-specific controls. Missing, disabled, mismatched or unsupported fields stop before the write. Validate the full task contract against approval. Fixture and authorized live canary evidence must agree. Do not enable this channel for public use while missing fields can silently retain platform defaults.

### R12 — Complete operational observability and readiness — 6/10 — Launch gate / incomplete checks

**Evidence:** `backend/app/main.py:82` health always returns OK. `/api/ready` probes DB connectivity and only the `generation_work` table plus broker ping, not the full migration head. Compose health checks use `/api/health`, and Celery service health checks are disabled. Repository inventory found logging and local doctor/heartbeat features, but no complete instrumented SLO/alerting service.

**Done when:** Measure queue age, provider errors, generation exhaustion, uncertain writes, task latency and cost; wire alerts and runbooks; readiness checks the expected schema and actual service admission; deployment drains/unhealthy routing are tested. Liveness staying up during DB loss is acceptable only when readiness is separately honored.

### R13 — Reserve monthly Freelancer quota atomically and by account — 6/10 — Confirmed quota defect

**Evidence:** `backend/app/adapters/freelancer.py:164` stores quota under the tenant/platform key `bid_quota`, without principal. `:183` checks remaining quota before awaiting the external API; `:198` increments afterward. P6 lets two concurrent calls reach the external-write mock with a monthly limit of one. `StateStore.set` is read/modify/write rather than a quota reservation.

**Done when:** Reserve before dispatch under the correct account identity, reconcile confirmed/uncertain results deliberately, use configurable/provider-observed entitlements, and pass PostgreSQL concurrent-admission tests. Per-second pacing and daily action caps do not fix this monthly race.

### R14 — Add tenant-level generation metering and cost limits — 6/10 — Missing production control

**Evidence:** `backend/app/textgen.py:96` uses a global `llm:tokens` bucket. On Redis operation errors it admits the request; its local fallback is per process. `generateText` does not take a tenant identity or reserve a tenant budget.

**Done when:** Attribute generation usage to tenants/jobs, enforce fair concurrency and explicit spending/usage caps across processes, account for retries, and report actionable limits. The existing global requests-per-minute setting is useful but does not prevent one tenant from exhausting shared allowance or constrain per-tenant paid usage.

### R15 — Correct and complete outcome/reply polling — 6/10 — Confirmed detection defect / bounded coverage gap

**Evidence:** `backend/app/outcome_sync.py:78` rejects our own sender but accepts missing senders as someone else's reply; P3 proves this. `:133` always retrieves only offsets 0–200, with no thread pagination cursor carried to subsequent ticks. Proposal cursoring is separate and does not extend thread coverage.

**Done when:** Require an identified relevant sender and valid event data, traverse account threads incrementally or query by project, reconcile duplicates/outcomes idempotently and expose polling freshness. A relevant thread beyond the first 250 can otherwise remain unexamined indefinitely under stable ordering.

### R16 — Complete digest delivery and reminders — 6/10 — Unfinished delivery workflow

**Evidence:** `backend/app/digest.py:70` requires operator-maintained verified-recipient JSON. A durable reservation is committed before SMTP with no delivery-state/reconciliation workflow; failures can consume the window. Daily due time is fixed to the 07:00 UTC hour. `due_at` for Workbench conversations/client notes is stored and shown but repository searches found no scheduler/reminder consumer for those fields.

**Done when:** Connect verified recipients to user settings, record pending/sent/failed/uncertain delivery, retry only confirmed-safe failures, support expected scheduling/timezones, and deliver/display due reminders. Preserve the protection against blindly retrying uncertain SMTP outcomes.

### R17 — Finish team workflow and long-lived record access — 6/10 — Incomplete product

**Evidence:** `backend/app/teamwork.py` implements accepted memberships and exact draft review, with export rather than dispatch integration. `:226` returns only the newest 200 drafts; there is no corresponding older-draft pagination route or has-more flag. Team ownership transfer/archive/delete and a direct reviewed handoff into an owned proposal workflow are absent from this router. Frontend explains the manual export boundary.

**Done when:** Provide archive/pagination, member lifecycle and an intentional approval-preserving handoff; keep private credentials isolated. Full shared-account dispatch is an expansion feature, not permission to bypass the owner's review boundary.

### R18 — Finish trustworthy experiment and revenue analysis — 6/10 — First-release limitations

**Evidence:** `backend/app/workbench.py:120` exposure validation verifies ownership, confirmed submission and experiment approval, but not that the submitted content actually used the claimed variant. `:466` reports user-recorded observational exposures, including unresolved outcomes in the exposure denominator. `:513` aggregates manual receipts and unreported costs remain excluded. Reports stop above 20,000 exposures/10,000 receipts.

**Done when:** Preserve variant/version provenance and event timestamps, show pending outcomes and comparable observation windows, support complete paginated/aggregated reports and attributable cost imports. Continue labeling observational/manual data honestly; randomized tests or predictive ranking are separate research, not promised revenue lift.

### R19 — Delete platform credentials with the platform account — 5/10 — Confirmed security/lifecycle defect

**Evidence:** `backend/app/routers/orchestration.py:141` only deletes `PlatformAccount`; `AdapterCredential` has a user FK, not an account FK (`models.py:181`). P1 deletes an account and successfully loads its retained synthetic vault credential via legacy default-principal selection. The separate explicit credential-delete endpoint does remove it.

**Done when:** Account removal transactionally revokes the credential/configuration authority and invalidates dependent pending work, with clear re-enrollment behavior and audit evidence. ### R20 — Finish structured payload validation and legacy UI resilience — 5/10 — Statically confirmed failure paths

**Evidence:** `backend/app/schemas.py:366` exposes portfolio matches and analysis as untyped dicts. `frontend/src/views/ProposalQueue.tsx:683` directly renders `analysis.tone`; `:843` dereferences each portfolio-match value. **Done when:** Validate external/LLM record shapes and reasonable request limits at boundaries, normalize historical records and make the renderer tolerate unknown data. Add malformed-record browser coverage. These cases are static code proofs; today's successful UI fixture did not contain them.

### R21 — Finish Workbench collection access and evidence search — 5/10 — Functional truncation / unfinished UI

The records API already supports keyset pagination, but the UI does not use it.

**Done when:** Provide next-page/search/filter/export controls in the app and complete evidence matching or an explicit supported-bound error. Large collections must not quietly hide useful proof or require customers to call APIs for routine editing.

### R22 — Preserve the actual base of an unsaved proposal draft — 5/10 — Static state-management defect

**Evidence:** `frontend/src/hooks/useDrafts.ts:59` writes current item revision/text alongside an existing edit whenever items refresh. It does not preserve the original stored base. Restoring then compares against that relabeled base. The edit's own base revision provides a separate approval guard, so this is not evidence of a server approval bypass.

**Done when:** Persist the actual edit-origin revision/text, surface conflicts without losing text, and provide explicit discard/rebase choices; test server refresh, logout/login and stale-review recovery in the browser.

## Proposed execution after approval

1. **Protect external actions:** R11, R24, R06, R13, R19, R25. Add the reproduced failures as regression cases while fixing one item at a time. Keep real submission channels gated until the relevant fixes and channel canaries pass.
2. **Restore complete, correct workflows:** R07, R02, R15, R20, R22, R26, R29, R30. Verify recovery and exact review boundaries, including PostgreSQL races where relevant.
3. **Prepare a supportable customer pilot:** R10, R14, R16, R17, R21, R27, R28. Complete user journeys and explicitly scope any larger collaboration/automation expansion.
4. **Qualify deployment:** R05, R09, R12, R03, R23 and R01. Set a measurable initial capacity and run controlled canaries, restore drills and current dependency checks against the release candidate. Historical live-data reconciliation is a separate read-only inventory followed by an approved data operation.
5. **Commercial and reporting completion:** R04 if selling hosted access, R08 and R18 to the precision/provenance level actually promised, then R31 across the final scope. Billing can be developed earlier in parallel logically, but should not unlock an unsafe production channel.
6. **Expand marketing only after evidence:** Publish the proven supported capabilities and measure activation, time to first useful draft, confirmed submissions, actual customer receipts, support burden and operating cost. No test suite or feature count establishes future revenue.

Approval should cover the ranked register and the execution sequence. Items marked conditional/expansion need a deliberate product scope, not an assumption that every large feature must precede first revenue. No implementation has begun in this audit.
