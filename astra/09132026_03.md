# Continuation findings: account identity and Freelancer provider contracts

Date: September 13, 2026. These findings extend R01/R02/R15 in the original audit; they do not add an invented live qualification claim. All requests used for this research fetched public documentation. No provider credentials, messages or bids were sent.

## Confirmed provider contract mismatches

The original adapter's tests repeated several implementation assumptions. The official provider material supplies an independent comparison:

| Surface | Repository behavior before correction | Provider evidence / corrected contract |
|---|---|---|
| API authentication | Standard Bearer header | The official SDK uses `Freelancer-OAuth-V1` for API requests. The adapter and request-capture tests now match it. |
| OAuth authorization | `/oauth/authorise` | The official developer portal uses `/oauth/authorize`. |
| OAuth exchange/refresh | Appended `/oauth/token` to the API base on `www.freelancer.com` | The developer portal posts to `https://accounts.freelancer.com/oauth/token`, separately from the resource API base. Both exchange and refresh now use that endpoint. |
| Thread retrieval | `/api/projects/0.1/threads/` | The SDK and developer portal specify `/api/messages/0.1/threads/`. Requests now ask for message/context details. |
| Project context | Expected a flat project field | SDK fixtures and portal schemas show a wrapper containing `thread.context`, with a context type and ID. Non-project contexts are excluded. |
| Message payload | Expected only `last_message.time` | The portal response schema includes wrapper `messages` and nested thread `message`, with `time_created` and `from_user`. SDK examples also contain `from_user_id`. The parser accepts these documented forms and existing normalized records, validates identity/time/content, and does not treat our own latest message as a client reply. |
| Bid status | GET a guessed single-bid path and read `status` | The documented collection supports a bid-ID filter. Its bid schema uses `award_status` for awarded/rejected state. The adapter retrieves the requested bid from that collection and rejects a missing/mismatched ID. |

Its authentication examples and embedded response schemas were inspected directly. The bundle is a dated source artifact, not a promise that a URL or schema remains unchanged forever.

The OAuth and message-field corrections follow the provider's own portal content, not a third-party tutorial. The SDK repository is older than the current portal; where examples differ, the parser accepts both explicit, validated identities. Live app permissions, sandbox OAuth behavior, provider entitlement and receipt semantics still require deployment/account qualification under R01.

## Additional implementation defects found and addressed

1. Multi-account dispatch could select one credential principal while reading another account's bidder/member defaults. Review now binds account identity, and dispatch consumes the reviewed identity. A mock-transport-independent dispatch regression verifies the second principal and bidder.
2. An explicitly bound browser task could be overwritten with the only enabled account during insert. Explicit IDs now survive insertion; claim authorization rejects missing/foreign/unavailable identities.
3. Agency roster storage was tenant-wide even when a specific agency account was selected. New rosters are principal-specific. Historical unscoped records remain unassigned until the owner explicitly assigns them through Accounts. Assignment happens once and will not overwrite an existing populated roster. Concurrent additions serialize on the owner; state upserts avoid select/insert races.
4. Browser status tasks combined proposals from different accounts. New tasks group by reviewed identity; unresolved historical ambiguity is logged rather than guessed. Fiverr fetch tasks carry their own account/username, and generated offers retain source account information.
5. Reply polling repeatedly visited only the first 250 threads. A durable account-specific cursor now advances through bounded pages; each page matches all relevant submitted proposals, independently of the bid-status cursor. This avoids two rotating cursors repeatedly missing each other's records.
6. Reply detection previously accepted an absent sender as a client. It now requires a known matching client identity, a matching project, a valid timestamp after submission, and actual message text. A conditional database write prevents duplicate notifications from concurrent polls. Polling freshness and failures are visible on the selected Freelancer account.
7. Numeric platform-account IDs can be reused in SQLite. Account identity epochs now distinguish deletion/recreation, and both delayed vault writes and OAuth state are bound to that identity.
8. Indeed was presented alongside implemented discovery channels. It now has an explicit manual-import/tracking scope, no new account connector enrollment, and separate capability documentation. Historical records remain readable.

## Verification limits

The committed evidence directory contains intermediate failures as well as later results. A failed fixture, selector or disposable-service startup is not a passing check. Use the most recent **completed** full-suite/browser logs named in `09132026_02.md`.

Remaining R01/R15 limits include account-specific live response qualification, polling behavior under changing provider ordering, and message history beyond the messages included with a thread response. Unknown client identities deliberately do not generate client-reply alerts. These limits must not be described as a complete, live-certified messaging integration.
