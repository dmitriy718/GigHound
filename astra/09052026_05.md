## Changes and audit coverage

### A004/A041 — per-claim fencing and scoped status results

`StealthTask.claim_token` is a new nullable 64-character column. A successful claim generates a cryptographically random token; a reclaim clears the previous token and the next claim generates another. Tokens are returned only by the claim endpoint, not by task polling. Worker completion requires the claiming worker ID, exact token and an unexpired claim. The conditional completion update includes the token, preventing an older attempt from completing a newer claim even when both processes use the same worker ID.

Claims expire after 15 minutes, matching the existing reaper timeout. Missing tokens on pre-upgrade claimed rows fail closed. The worker requires a token in the claim response, carries it on authorization, completion and status-scrape requests, and keeps at most one current claim because its runner is sequential.

Status-scrape results must belong to the claimed payload's `items`, tenant and platform. The endpoint checks the lease, locks the task row, and rejects subsequent posts after completion with 409. Out-of-task results reject the batch before applying outcomes. Existing tests were changed from silently skipping foreign items to expecting rejection. Existing outcome helpers still contain internal commits; this change is not a claim of a fully transactional outcome-learning pipeline.

### A014/A020, partial — account and session gates

Claiming browser work now requires an active user and an enabled `stealth` or `hybrid` account. A new authorization endpoint repeats those checks, validates the lease and honors an open tenant/global circuit without consuming a half-open trial token.

The bundled worker calls authorization before entering any handler and immediately before Upwork submission, opted-in manual-assist submission and gig draft save. This covers reused browser contexts as well as fresh ones. Session reads require the current worker ID and claim token, passed in headers rather than query-string secrets, and recheck the account. An API-only account does not implicitly authorize browser work.

Browser session fetch failures now propagate instead of restoring access through a cached local profile. The explicit CLI login flow without a backend client remains separate.

Limits: tasks still identify tenant/platform rather than one immutable account ID. With multiple active accounts, removing one does not necessarily disable the platform; exact account/principal binding is still open. A check immediately before a click cannot atomically fence the external website against a simultaneous account change. The shared pool bearer token and other result-ingest endpoints still need per-worker capabilities and payload binding. No claim that all of A014/A020 is closed.

### A007/A010, partial — truthful uncertainty after an attempted write

The worker tracks whether it has reached an external submission click. Handler failures before that point explicitly report `submitted: false`; failures after it report `submitted: null` and `submitted_unverified`. This includes timeout/challenge errors after an attempted click. The backend conservatively classifies a failed submission with no explicit non-submission verdict as uncertain, preserving the batch-1 no-replay boundary.

An opted-in manual-assist click is no longer treated as proof of successful submission. It uses confirmation/failure markers, otherwise returning an uncertain result. The UI-facing note tells the user to check the platform before another attempt; it does not tell them to click Submit again after an uncertain result. Preview-only work reports `manual_action_required` and instructs manual submission through the platform.

Limits: no persistent interactive handoff has been implemented; the worker still closes task pages. Provider receipts and independently verified submissions remain open. Gig-draft save verification and structured Fiverr form support remain open.

## Additional finding A063 — PostgreSQL migration/model drift

**Proof:** `backend/alembic/versions/7c1e9a2b4d38_add_bid_advice_to_proposal_queue.py` creates `proposal_queue.bid_advice` with `sa.JSON()`. `backend/app/models.py` defines it with `JSONType`, whose PostgreSQL variant is JSONB. On a fresh PostgreSQL 16.15 migration, `alembic check` reported a type change for this exact column. SQLite did not expose the mismatch.

**Fix:** forward migration `a6c3d9e20b18` converts only this PostgreSQL column using `bid_advice::jsonb`; downgrade converts it back to JSON. SQLite is unchanged. The historical migration is preserved. CI's PostgreSQL migration smoke now runs `alembic check`, catching future model/migration drift.

**Evidence:** a populated fixture containing a fractional amount, Unicode text, null, a list and a nested Boolean retained the same decoded values. PostgreSQL metadata reported `jsonb`. Upgrade/downgrade/upgrade succeeded. The cast normalizes JSON object representation; it does not preserve object-key ordering or duplicate JSON keys. A large-table conversion needs a deployment maintenance/locking assessment.

## Rollout and rollback contract

1. Pause/drain workers before rollout. Preserve a restorable production database backup and vault key using the existing operations process; no production backup was claimed or attempted here.
2. Inspect existing claimed submissions and reconcile ambiguous external outcomes. Old claim rows have no lease token and cannot be completed by the new protocol; allow the reaper to resolve them conservatively rather than resetting writes to pending.
3. Apply migrations through `a6c3d9e20b18`, then start the matching backend and worker version. Do not mix protocol versions: old workers cannot supply claim tokens, and new workers reject a backend that does not issue them.
4. Ensure intended browser accounts use `stealth` or `hybrid` mode. API-only, missing, disabled and inactive-user accounts will not run browser tasks. Pending tasks are retained so an operator can correct configuration.
5. Verify claim → authorize → session → result on synthetic/read-only work before enabling real external actions.
6. Before rollback, stop/drain workers and reconcile writes again. Downgrading removes claim tokens; restarting the old automatic replay behavior on unresolved tasks would reintroduce the audited duplicate risk. Prefer a forward fix while keeping workers paused.

The migration and code are implemented locally, not deployed. P1 is still incomplete: immutable approved account/version snapshots, exact account binding, complete manual handoff and Fiverr forms remain priorities. P2–P7 and the ten proposed features remain open as detailed in `09052026_02.md`.
