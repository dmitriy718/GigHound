## Freelancer refresh-token retention (R19/R20 continuation)

Confirmed by source inspection: `_persist_tokens` previously used `payload.get('refresh_token')` even on refresh, erasing the existing refresh token when the server did not supply a replacement. OAuth permits that omission: [RFC 6749 section 6](https://www.rfc-editor.org/rfc/rfc6749#section-6), retrieved September 13, 2026, makes issuing a new refresh token optional and specifies replacement when one is issued.

The refresh path now passes the token used for that exchange as fallback. A supplied replacement still wins. Initial enrollment does not inherit another credential's token. Validation rejects malformed token values and expiry data before the vault write; existing credential-version and account-identity checks remain intact. Expiry skew is bounded for short-lived tokens instead of making a thirty-second token immediately expired.

Proof: 136 adapter/credential/audit regressions passed (`post-push-refresh-final.log`), including two successive refreshes when replacement is omitted, short-lived token reuse, and malformed responses preserving the stored credentials. The initial added test used the wrong adapter cleanup method; corrected to the existing `close()` method before the successful rerun. These are synthetic HTTP responses, not a live Freelancer qualification.
